# 站内搜索能力规划（xinhua-hub）

> 状态：方案设计阶段（V4.0 提出，尚未开发）。目标：未来用户搜索「养老」「分红」「香港保险」「客户异议」等关键词，30 秒内定位资料。

## 一、需求背景

当前站点已有内容类型：

| 类型 | 示例 | 数量级 |
|------|------|--------|
| 演算器 | calculator-*.html（5 款核心 + 其他） | 10+ |
| 红利资料 | dividend / hongli-* / hongli-realization | 4 |
| 销售问答 | sales-qa + 6 子页 | 7 |
| 培训中心 | training.html（数据驱动）+ files/ | 6+ |
| 公司/产品 | company-intro / product-qa-handbook / intro-* | 若干 |

痛点：内容分散在多个 HTML，用户只能靠首页入口逐级找，无法"搜关键词直达"。

## 二、技术选型（纯前端静态，契合 GitHub Pages）

GitHub Pages 无服务端，搜索必须前端实现。两种路径：

### 方案 A：运行时索引（推荐，轻量）
- 建 `assets/data/search-index.json`，每条记录：`{title, url, category, tags, summary, keywords}`
- 首页搜索框输入 → 前端 `fetch` 该 JSON → 本地模糊匹配（标题/标签/关键词）→ 弹结果列表
- 优点：无需构建步骤，新增内容只改 JSON；体积小（全站索引 < 50KB）
- 缺点：全站全文检索弱（仅元数据级），但覆盖 90% 场景

### 方案 B：构建期全文索引
- 用 Node 脚本扫描所有 HTML，提取正文文本生成倒排索引（lunr.js / flexsearch）
- 优点：支持正文全文搜
- 缺点：需构建步骤，部署流程变复杂

**结论**：先上方案 A（元数据 + 标签检索），覆盖「养老/分红/香港保险/客户异议」等导航型搜索；若后续需要正文级检索再升级方案 B。

## 三、数据准备

复用现有结构：
- `training.json` 已含课程 title/category/tags → 直接并入搜索索引
- 各演算器、红利页、销售问答子页补充 `tags` + `summary` 元数据
- 在 `assets/data/search-index.json` 汇总

索引条目示例：
```json
{
  "title": "宏愿人生养老年金",
  "url": "calculator-hongyuan.html",
  "category": "演算器",
  "tags": ["养老", "年金", "分红型", "现金流"],
  "summary": "分红型养老年金，55/60/65/70岁起领，适配养老规划客群"
}
```

## 四、交互设计

- 首页搜索框（已存在 `.search-wrap`，V3.1 预留）→ 输入即过滤
- 结果以浮层卡片展示：标题 + 分类标签 + 摘要 + 跳转
- 支持「回车进入搜索结果页 `search.html`」展示完整列表（未来页）
- 移动端：搜索框固定在首屏下方，点击展开键盘

## 五、实施步骤（未来执行）

1. 汇总 `search-index.json`（脚本从各页 `<meta>` + training.json 生成）
2. 写 `assets/js/search.js`（轻量模糊匹配，无第三方依赖）
3. 首页搜索框接 `search.js`，弹浮层结果
4. 验收：搜索「养老」→ 命中宏愿/养老规划页；「分红」→ 红利区+分红险逻辑；「香港保险」→ 家庭规划页；「客户异议」→ 客户异议处理页

## 六、风险与取舍

- 静态站无后端，搜索仅限已索引元数据（不搜正文隐藏内容）——可接受，导航型搜索为主
- `search-index.json` 需随内容更新维护（可脚本半自动生成，降低人工）
- 不引入重型搜索库，保持站点轻量、加载快
